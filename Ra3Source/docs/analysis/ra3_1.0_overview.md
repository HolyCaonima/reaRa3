# ra3_1.0.game 首次分析总体报告

> 分析对象：`D:\Game\Ra3\Game\Data\ra3_1.0.game`（只读，未做任何改动）
> 数据与脚本：本目录 `ra3_1.0/`、`tools/pe/`、`tools/ghidra/`；大体量中间产物在仓库根 `work/`（已 gitignore）
> 标注约定：**[程序]** = 反编译/反汇编游戏代码得到的结论；**[数据]** = 用 Ra3Source 代码对实际游戏数据跑通验证；**[推断]** = 尚未直接证实。

## 1. 摘要

- 主程序是 VS2005（链接器 8.0）编译的 32 位 GUI 程序，原名 `RTS-final.exe`，构建于 2008-10-10。没有 PDB/调试信息，游戏类也没有 RTTI。
- SecuROM 的影响比"整体加壳"小得多：`.text` 里约 810 万字节的原始代码是明文，熵值 6.64，Ghidra 识别出 30,496 个函数。被 SecuROM 改动的是**零散的单条指令**：约 1,360 处被替换成 `JMP dword ptr [.securom 指针槽]`，分布在约 1,200 个函数里，约占 `.text` 函数总数的 4%。其中一部分函数只是开头那条指令被换掉，主体仍在 `.text` 里；另有约 530 个函数入口之后看起来是垃圾字节，主体大概率无法静态读取（启发式统计，详见第 5 节）。
- 原始源码树能从断言和日志字符串里恢复出 191 个源文件路径，覆盖 SageEngine（gamelogic/gameclient/common/gamenetwork）、W3DDevice、SageRender、assetmanager 等模块。
- 资源加载链已经从程序层面打通：SkuDef 指令 → `BigHandler` 挂载 `.big` → 档案内查找 → RefPack 解压。Ra3Source 的 `io` 模块已按反编译结果对齐，并在全部 14 个档案、15,329 个条目上通过验证。

## 5. SecuROM 的影响

1. **入口与导入。** 入口点在 `.securom`。导入目录（0x02AA05F0）也在 `.securom`，共 22 个 DLL，比原始导入表多了 `VERSION.dll`、`WSOCK32.dll`，`KERNEL32`、`USER32`、`ADVAPI32` 的函数也更多。原始导入表还在：20 个 DLL，IAT 位于 `.rdata` 的 0x00BBA000，名称完整，包括 d3d9、d3dx9_35、DINPUT8、DSOUND、XINPUT1_3、WS2_32、WININET 等。
2. **指令替换。** 原始代码里有 1,359 条跳转指令跳进 SecuROM 区域，几乎全是 `JMP dword ptr [0x018Exxxx–0x018Fxxxx]`。它们分布在 1,206 个函数里，另有 152 条不在 Ghidra 识别的任何函数里。按引用计数是 2,491 条，因为每条间接跳转会同时产生一条指向指针槽的引用（1,233 条）和一条指向槽中目标的引用（1,235 条）。槽的值在文件里基本都能直接读到，目标都是 `.securom` 里的桩代码：1,165 个以 `PUSH imm32` 开头，36 个以 `MOV` 开头，还有少量 `SUB`、`LEA`；目标处没有指令的只有 14 个。
3. **被替换后，原函数还剩多少？** 用 `ProbeSecuromThunkBodies.java` 从跳转指令之后开始线性反汇编：
   - **位于函数入口的 774 条**（Ghidra 把这些函数命名为 `thunk_FUN_019…`）：
     - 89 条后面是填充字节；
     - 153 条后面紧跟着至少 6 条合法指令，符合"只替换了开头那条指令"的情况。已人工确认的例子是 0x004D18F0 和 0x004D1D50：6 字节的 `JMP` 顶替了一条 6 字节指令（推测是 `sub esp, imm32`），后面的 `push ebx; push ebp; push esi; mov esi,[esp+0x620]…` 完整保留；
     - 其余 532 条之后只能解码出 0 到 5 条指令，就中断或跳到别处，看起来像填充的垃圾字节。这是启发式判断，没有逐个确认，其中也可能有本来就很短、以跳转结尾的合法代码。这些函数的主体**大概率无法从 `.text` 静态读取**。
   - **位于函数中间的 585 条**：290 条之后能线性走到 `RET`，说明只是中间某条指令被替换，其余部分完好。
4. **对逆向的影响。** 约 96% 的 `.text` 函数没有受影响，可以直接反编译。对于受影响的函数：
   - 只丢了开头指令的，可以根据栈偏移等上下文人工补全，然后照常分析；
   - 主体读不到的，只能从调用方、数据格式和运行行为来重建。
   - 另外，如果一个函数的调用方是被替换过的代码，或者它只通过虚表被调用，Ghidra 常常不会把它建成函数，需要用 `entry:` 选择器手动建。第 8 节里的 0x004D1B60、0x009F5AF0、0x009F5F80 都是这样补出来的。
5. **边界。** 本项目**不做** SecuROM 的脱壳、解密、绕过，也不分析 `Stext`、`Sdata`、`.securom` 里的保护代码。这里的统计只是读取并描述文件中已有的明文内容。

同一路径出现在多个档案里的有 226 个：

- 218 个在 `Shaders.big` 和 `Misc.big` 之间，存储大小都相同，`Shaders.big` 胜出；
- 8 个在 `Misc.big` 和 `WBData.big` 之间，都是编辑器模型，编码不同（例如 `bowl.w3d` 一份是 RefPack 压缩的 21,660 字节，一份是未压缩的 30,346 字节），`Misc.big` 胜出。

`ra3tool find <路径>` 会标出 `used`（游戏实际使用的那份）和 `shadowed`（被遮蔽的）。

**档案内容。** 257 组编译后的资源流，每组都由 `.manifest`、`.bin`、`.relo`、`.imp` 四个文件组成，覆盖地图、Apt、StaticStream、GlobalStream 等；另有 12,043 个 `.cdata`（主要是语音）、928 个 `.tga`、575 个 `.snd`、344 个 `.dep` 加 272 个 `.fxo`（着色器）、1 个 `.csf`（`gamestrings.csf`，RefPack 解压后以 ` FSC` 开头，[数据]）。[推断] 这些资源流由 `Libraries\Source\assetmanager` 解析，是下一阶段的主要目标。

**已知偏差。** 下面这些地方，Ra3Source 和游戏的行为不完全一样，已经写进对应头文件的注释：

- `BigArchive` 只支持 32 位字段的 `BIG4`/`BIGF`，不支持 `Viv4`、`C0FB` 和其他宽度；
- `BigArchive` 比游戏更严格：会校验档案大小字段、拒绝重复路径、要求条目表正好结束在头部末尾，这三项游戏都不检查；
- RefPack 标志 `0x01`（带压缩长度字段）在游戏里处理不一致：一次性解码器会跳过这个字段，另外两条路径不跳过。Ra3Source 跟随一次性解码器。已检查的发行数据里都没有设置这个标志。

## 10. 未知项与限制

- 约 530 个被 SecuROM 替换了入口的函数，主体大概率无法静态读取（启发式统计，未逐个确认）；所有被替换掉的原始指令都看不到。
- SkuDef 读行循环、`add-bigs` 目录挂载、路径拼接（0x01955730）都在 SecuROM 跳转函数之后，具体实现不可见。
- 游戏在调用 `BigHandler` 之前，由哪一层把 `/` 统一成 `\` 还不清楚。档案内的比较不区分斜杠方向，Ra3Source 的 `find` 额外把 `/` 和 `\` 视为相同。
- BIG 尾部后 4 字节的含义还未知。
- `rts.ver`、`.rsrc` 和 `Data\dfe` 都还没有分析，[推断] `Data\dfe` 是 SecuROM 的 DFE 组件。
- 虚函数调用的目标大多没有被 Ghidra 建成函数（游戏类没有 RTTI，Ghidra 也不会顺着虚表建函数）。需要按虚表逐个用 `entry:` 补，或者写脚本批量处理。
